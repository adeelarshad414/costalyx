# 13-BILLING-AGENT-SPEC.md — Milestone I: Agentic Billing Intelligence

## Purpose
Adds a new milestone (I) to Costalyx: an **agentic billing layer** that
(a) continuously catches price and spend anomalies, and (b) handles
stakeholder invoicing — showback/chargeback statements generated, explained,
and routed to the right owners — reimagined as an agent loop rather than a
static report. This document is additive to 01-SPEC.md; it does not modify
Milestones A–H. All hard constraints from docs 00–12 remain in force.

## Positioning ("reimagined" — what makes this different)
Incumbents (Cloudability, CloudZero, Flexera) treat anomalies as a list you
check and invoices as a PDF you download. Costalyx's Billing Agent treats
both as an **observe → reason → explain → propose → (approved) act** loop:

- Every anomaly arrives with a machine-generated *explanation and evidence
  chain* (which accounts, which resources, which pricing rows, what changed,
  since when) — not just a red dot on a chart.
- Every invoice/statement is generated, reconciled against ingested billing
  truth, annotated with variances vs. the prior period, and routed to the
  stakeholder who owns that cost — with the agent drafting the narrative a
  FinOps analyst would otherwise write by hand.
- Every agent action is trust-tier gated (05-RBAC-TRUST-TIERS.md): the agent
  drafts and proposes autonomously; it never sends an invoice or notifies an
  external stakeholder without the tier-appropriate approval.

## Sub-milestone I.1 — Anomaly Detection Engine

### Detection scope (v1, rule/statistical — ML remains a later phase)
1. **Unit-price anomalies:** a resource's effective `hourly_rate_usd`
   changes vs. its own temporal pricing history (`valid_from`/`valid_to`
   rows) beyond a configurable threshold — catches provider price changes,
   lost discounts, expired RIs/Savings Plans silently reverting to on-demand
2. **Usage anomalies:** daily usage-hours for an (account, service,
   usage_family) tuple deviates beyond N median-absolute-deviations from a
   trailing window (default 28 days; both window and N are tenant-config)
3. **New-spend anomalies:** first-ever cost rows for a (account, service)
   pair above a floor — catches accidental new-region/new-service spend
4. **Commitment-coverage anomalies:** coverage ratio drops below a
   tenant-set floor (ties into Milestone E data, no new ingestion needed)

### Anomaly record (additive schema)
`anomalies` table:
`id, tenant_id, type (unit_price | usage | new_spend | coverage),
severity (low | medium | high), status (open | acknowledged | resolved |
false_positive), detected_at, window_start, window_end,
evidence_json, explanation_md, assigned_owner_id (nullable)`

`evidence_json` must reference actual `cost_records` ids and pricing rows —
an anomaly with no traceable evidence rows is a defect, consistent with the
evidence-over-assertion principle used across the whole platform.

### Explanation requirement (the agentic part)
For each anomaly, the agent produces `explanation_md`: a short, plain-
language narrative ("RDS in account X began billing at the on-demand rate
on <date>; a 1-yr RI covering it expired on <date-1>; projected monthly
impact $N at 730 h/mo") generated from the evidence chain. Where an LLM is
used for narrative generation, the numbers in the narrative are **computed
by deterministic code and interpolated into the text — never generated by
the model** — so the prose can't contradict the math. A validation step
re-parses every numeric claim in the narrative and asserts it matches the
computed evidence before the anomaly is published; mismatch = generation
retry, then fallback to a deterministic template.

### False-positive learning loop (v1, deterministic)
Marking an anomaly `false_positive` requires a reason code (seasonal,
planned_change, known_migration, other+note). Reason codes feed per-tenant
suppression rules (e.g., auto-suppress usage anomalies for a tagged
migration window). No opaque ML feedback in v1 — suppression rules are
inspectable rows in a `anomaly_suppressions` table.

### Acceptance criteria (I.1)
- Golden fixture set includes at least one seeded example of each of the
  four anomaly types; the engine detects all four and zero false anomalies
  on the clean control fixture
- Every detected anomaly's `evidence_json` resolves to real cost/pricing
  rows (integration test walks the references)
- Numeric-claim validation on `explanation_md` has 100% branch coverage
  (this is pricing-math-adjacent code — same zero-tolerance class as the
  cost computation modules in 08-TESTING-STRATEGY.md)
- Anomaly events published to a new Redpanda topic
  `costalyx.billing-agent` for downstream notification consumers

## Sub-milestone I.2 — Stakeholder Invoicing & Statements

### Concepts (additive schema)
- `stakeholders`: `id, tenant_id, name, email, role_label (e.g. BU owner,
  project lead, CFO), notification_channel (email | none in v1)`
- `billing_scopes`: maps a stakeholder to what they own — an account group,
  a dimension value (e.g. team=payments), or a saved View. One stakeholder
  may own many scopes; scopes may overlap (overlaps are flagged, not
  silently double-billed — see acceptance criteria)
- `statements`: `id, tenant_id, stakeholder_id, period_start, period_end,
  status (draft | pending_approval | approved | sent | disputed | void),
  totals_json, narrative_md, generated_at, approved_by (nullable),
  sent_at (nullable), line_items_ref`
- `statement_line_items`: append-only; every line traces to aggregations
  over `cost_records` (never hand-entered amounts; manual adjustments are a
  distinct line type `adjustment` with mandatory note and audit-log entry)

### Agent workflow (trust-tier mapping)
| Step | Autonomy | Tier |
|---|---|---|
| Generate draft statement per stakeholder per period (scheduled) | Fully autonomous | Deterministic |
| Reconcile draft totals against cost_records; attach variance-vs-prior-period narrative | Fully autonomous | Deterministic (numbers) + validated generation (prose, same numeric-claim validation as I.1) |
| Flag scope overlaps / unallocated remainder | Fully autonomous | Deterministic |
| Move statement to `pending_approval` and notify internal approver | Fully autonomous | Deterministic |
| **Send** statement to stakeholder / external channel | **Requires explicit human approval** per statement (or a tenant-admin-enabled per-scope standing approval, itself an audited admin action) | Generated-tier action: never auto-executed |
| Handle dispute: stakeholder marks disputed → agent re-reconciles, produces diff report, routes to approver | Autonomous analysis, human resolution | Mixed |

The send step is deliberately conservative: invoicing external stakeholders
is a reputational/financial action, so it sits at the same
approval-required tier as cloud-mutating actions in 05-RBAC-TRUST-TIERS.md,
even though it's "just an email." A wrong invoice sent autonomously is a
worse failure than a delayed one.

### Statement content requirements
- Totals derived exclusively from `hourly_rate_usd × usage_hours`
  aggregations (730 h/mo for monthly derivations) — never a separately
  maintained invoice amount
- Variance section: top-5 movers vs. prior period with evidence links
- Anomaly cross-reference: any open anomaly overlapping the statement's
  scope and period is listed on the statement (a stakeholder should never
  be billed for a period containing an unexplained anomaly without seeing it)
- Unallocated remainder for the tenant is shown on an internal
  reconciliation view — statements across all stakeholders + unallocated
  must sum to tenant total to the cent (acceptance-tested)
- Export: PDF and CSV per statement; JetBrains Mono for all numerics

### Acceptance criteria (I.2)
- Fixture tenant with 3 stakeholders and overlapping scopes: overlap is
  flagged, and the sum-to-total reconciliation test passes to the cent
- A statement cannot reach `sent` status without an `approved_by` (or a
  standing approval row) — enforced server-side, integration-tested with
  each role below the required tier (per 05's penetration-test pattern)
- Dispute flow round-trips: disputed → re-reconciled diff produced →
  resolution recorded in audit_log
- All statement state transitions write hash-chained audit_log rows

## Sub-milestone I.3 — Agent Runtime & Guardrails

- The agent runs inside the existing scheduler worker (no new deployment
  unit): anomaly scan cadence and statement generation cadence are
  tenant-configurable cron-style settings
- Every agent decision cycle writes a row to an `agent_runs` ledger:
  `id, tenant_id, run_type, started_at, finished_at, inputs_summary,
  actions_taken, actions_proposed, errors` — the agent's own activity is as
  auditable as user activity (consistent with the run-evidence ledger
  already built for cloud connection validation in Milestone H)
- LLM usage (narrative generation only) goes through a single
  `NarrativeGeneratorService` behind a swappable interface with a
  deterministic-template fallback, so the platform is fully functional with
  the LLM disabled (self-hosters without an LLM key lose prose polish, not
  functionality). Provider API key, if configured, lives in Vault — dummy
  value `CHANGE_ME_DEV_ONLY` in dev, registered in DUMMY-VALUES.md
- Rate/blast-radius guards: per-run caps on notifications and statement
  sends (tenant-config, sane defaults), so a misconfigured scope can't
  mass-send hundreds of statements in one cycle

## Personas served (extends the 00-doc table)
- **FinOps Practitioner:** anomaly triage queue replaces manual daily spend
  review; statements replace hand-built chargeback spreadsheets
- **CFO/CEO:** statements arrive explained, with variances narrated
- **IT Manager:** scope ownership model formalizes showback/chargeback
- **SRE/DevOps:** commitment-expiry anomalies catch the silent-reversion
  failure mode before the monthly bill does

## Explicit non-goals (Milestone I)
- Payment collection / payment-gateway integration (statements are
  showback/chargeback instruments, not payment demands) — future phase
- ML-based anomaly detection (statistical/rule-based only in v1)
- Slack/webhook delivery channels (email only in v1; event schema already
  supports more via `costalyx.billing-agent` topic)
